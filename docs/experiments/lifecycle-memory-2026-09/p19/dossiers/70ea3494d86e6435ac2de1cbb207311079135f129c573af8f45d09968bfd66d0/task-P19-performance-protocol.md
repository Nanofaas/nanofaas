## Existing harness assessment

`docs/experiments/lifecycle-memory-2026-09/P07Calibration.java` is explicitly a historical factory/store microbenchmark. It directly constructs stores/factory, calls `markSuccess` and `settle`, and bypasses configured admission, HTTP decoding, controllers, actual dispatch and queue scheduling. T1 uses 20,000 warm-up operations, a two-second window and only the first 250,000 latency samples. Faster revisions therefore contribute a different fraction of their execution window to percentiles. Allocation is only the calling thread, and array allocation occurs inside the allocation interval. Its fixed-duration offered work differs by revision; retained outcomes and retention ages differ too. T2 completes only `"ok"` rather than the large/deep input as output and checks a tiny synthetic archive. It has no p99 or post-GC heap. Preserve its disclosed -35.1% throughput/+129.4% allocation concern as diagnostic evidence, not a present HTTP regression estimate or a neutral structural comparison.

`platform/control-plane/src/test/java/it/unimib/datai/nanofaas/controlplane/P07ConfiguredHttpCalibrationTest.java` is a useful correctness fixture: random-port Spring HTTP, real codecs/controller/queue/ownership and mocked LOCAL dispatch. Keep it as a gate and source of payloads/assertions, not the final performance engine:

- T1 has 100 warm-up requests and 1,000 sequential measured requests; its duration includes sampler start/stop and client/test work. It counts 2xx as admission without independently checking terminal result semantics. A serial closed-loop rate is not sustainable server throughput.
- T2 has no explicit warm-up, only 100 offers per shape, and holds dispatch completion until all offers finish. Reported latency is enqueue acknowledgement, including refusals, not execution latency. It reports neither elapsed useful throughput nor p99. The 63/100 large-shape admissions in the report must not be compared to 100/100 as equivalent useful work.
- Its allocation delta sums currently enumerated threads at two instants in a JVM shared with WebTestClient, Mockito, assertions, polling and sampling. Thread turnover can lose allocations or alter the set; virtual-thread coverage must be validated for the actual collector. A nonnegative result is not proof of complete process allocation accounting.
- Polling seven counters every 100 microseconds yields sampled lower bounds on peaks, not exact maxima or simultaneous snapshots. Drain checks only executions, canonical bytes, physical-copy bytes, waiters and live records. It does not check all physical resources or history.
- No GC checkpoint exists. Mockito invocation history and retained request/result objects can themselves retain payloads in this shared test JVM. A heap dump of that JVM cannot be labeled production control-plane retention.
- Profile assumptions deliberately skip one method depending on the build. A green invocation with a skipped scenario is not evidence for that scenario. Archive loss must be demonstrated for the replayed key before claiming replay-after-eviction coverage; accepting 202/410 alone does not establish that precondition.

## Harness and execution contract to freeze

Use one versioned external HTTP load generator and deterministic backend service, with server, generator, backend and each SDK runtime in separate processes. Build each production artifact outside measurement in isolated revision directories; capture source/archive and dependency hashes. Do not build or switch modules in a measured process. Do not mutate this dirty checkout to reconstruct A. Pin each module selection and its effective configuration separately; `all` does not cover sync-queue or container selection.

For direct LOCAL coverage, a bounded deterministic test-only handler adapter may be necessary. If used, archive its exact patch/binary and assert it changes only the downstream fixture, not admission or lifecycle. Also run a real EXTERNAL backend path. Do not relabel EXTERNAL as LOCAL. Both revisions receive identical wire requests, headers, payload bytes, function specifications, backend result/delay/error sequence and workload seed. Avoid copying a revision-specific Java test wholesale onto P00: its capacity APIs and constructor contracts do not exist there. Keep internal observer adapters separate from the shared black-box workload and validate their metric mappings.

Prebuild/prestart dependencies, verify health, then use a fixed warm-up policy selected in an unscored pilot. A practical starting proposal is 30 seconds warm-up and 60 seconds measurement, but freeze durations only after confirming stable throughput/latency segments and sufficient successful samples. Aim for at least 10,000 successful latency observations per ordinary scenario; extend both sides equally when needed. These numbers are protocol proposals, not requirements already measured. Failure to stabilize within a declared maximum makes a run inconclusive. Natural GC during measurement remains part of latency; exclude only deliberately induced diagnostic GC and warm-up.

Use a replayable open-loop arrival schedule with a finite client outstanding bound. Log intended send, actual send and generator lag; do not silently turn overload into a self-throttled workload. Use the identical request count, schedule and mix within each pair. Select a moderate common supported load where both sides admit and complete the intended cohort. Warm-up keys and measured keys must be disjoint, with equal warm-up work and equal checkpoint ages; either explicitly include warm retained state or let it expire identically. Do not invisibly clear production stores between phases.

A fixed moderate arrival rate naturally yields the same success/s on two healthy servers: it measures latency, cost and retention at equal work, not maximum throughput. Add a separate predefined load sweep to locate sustainable useful throughput with bounded backlog and a declared latency/failure criterion. Use the same rate grid for each revision and report offered/admitted/completed at each level. Never claim a capacity improvement just because one server responds with faster 429s.

Overload and lifecycle scenarios form a separate cohort. Equal offers cannot guarantee equal admissions when protections differ; report the difference, do not normalize it away or raise B's limits to imitate unbounded A. If a common admitted cohort cannot be produced without changing semantics, mark that comparison non-equivalent and retain the separate correctness/resource evidence.

Record exact Java vendor/build, GC, application JVM heap/flags (Gradle `-Xmx1g` is not the application's heap), CPU model/architecture and affinity, CPU quota/throttling, memory/cgroup limits, OS/kernel, container image digests, dependency lock/resolution data, runtime versions, host background load, network topology, backend resources and generator CPU. Keep all equal within the comparison. JVM/native and different SDK languages are distinct cohorts. The old `-Xms256m -Xmx256m` microbenchmark envelope need not suit a full HTTP application; choose and freeze a supported envelope without per-side tuning.

## Measurements and denominators

Retain request and execution identities so one logical execution is counted once across retries and replay. Record offered, actually sent, new admissions, replay hits, refused by HTTP status/error/resource, dispatch attempts, terminal successes/failures, waiter timeouts, cancellations and unresolved executions. Report client transport failures separately from server refusals. For a closed measured cohort, reconcile new admissions = terminal successes + terminal failures + unresolved, with cancellation classified by its actual logical outcome. Waiter timeout alone is not global execution failure.

Useful throughput is unique successful executions per second, not accepted enqueues, HTTP responses, attempts, polling or replay. Record both steady-window terminal success rate and fixed-cohort success rate from first scheduled offer through last terminal completion, explicitly including tail drain in the latter. Attribute all work by cohort; exclude warm-up completions. Preserve success bytes/s as well as executions/s for mixed payloads. Separate replay service rate from new execution rate.

Capture p50/p95/p99 for successful SYNC responses, ASYNC admission acknowledgements and ASYNC logical completion independently, plus refusal/failure/timeout distributions. Record count, unit, percentile convention and histogram precision; retain every request timing or lossless histogram counts across the full interval. Report send-to-response and intended-arrival-to-response when generator lag matters. Async polling introduces observation lag and additional server load: freeze its cadence, count it separately and report completion timestamps as observations/bounds unless an actual terminal event observer exists. Do not infer exact completion latency from a 202 response. Never average percentiles across runs; show each run and median/range of run-level metrics, with paired relative changes. Pool raw histograms only as an explicitly different aggregate view.

Allocation/success = server allocated bytes in the declared cohort interval divided by unique terminal successes in that interval/cohort, with boundary rules matching the numerator. For full cohort cost, measure through drain; provide a separate ordinary-window rate if useful. Include retry and failed-attempt costs; show failures/refusals alongside the ratio. Zero successes yields null with reason, not zero. The present ThreadMXBean calculation is observational only. Prefer a validated JVM-wide cumulative allocation counter on the chosen JDK, if available and demonstrated to include the thread types used; otherwise use a documented allocation profiler and label sampled/weighted estimates explicitly. Archive collector configuration and a short validation covering platform and virtual-thread allocation and thread exit. JFR allocation samples are not automatically exact allocated bytes; heap occupancy deltas are not allocation. Exact complete allocation/success is unavailable until a suitable collector is validated. Run profiling in identically instrumented paired passes and measure observer overhead separately; do not compare a profiled side to an unprofiled side.

Post-GC checkpoints: warmed idle baseline; end of offered traffic after logical/physical drain; after each relevant retention/eviction/cleanup window; after removal; and before/after shutdown using resources observable outside the process. Stop ordinary timing before diagnostic operations. Record checkpoint start/end, monotonic timestamp, GC count/cause and verified completion, used heap (not committed heap or RSS), live histogram and selected heap dump/root analysis. A GC request without observed collection is not a valid post-GC checkpoint. Repeat identical checkpoint policy on both sides. Explicit GC cannot expire a strongly retained cache entry or stop a non-cooperative worker; wait for the real configured policy, with a finite deadline, and report survivors if it expires. No post-exit heap sample exists: shutdown evidence comes from pre-exit observations plus externally observed process/thread/socket closure.

Collect RSS/PSS, direct-buffer memory, thread and socket populations separately from heap, per process. A heap histogram counts instances but does not assign retained ownership; use dominators and root paths for unexplained growth. Neither P16b command-level maximum RSS nor a Gradle worker's heap is runtime-only retained memory.

## Immutable P23 artifact contract

Create a versioned, content-addressed dossier, for example `p19-v1/<manifest-sha256>/`, then publish it to storage with retention/versioning or write-once policy. Hashes detect modification but do not themselves prevent it. Keep a source-controlled pointer containing immutable URI and manifest digest; never use a mutable STATO entry or `latest` tag as the only baseline identity. P23 creates a new dossier referencing the frozen P19 digest rather than overwriting it.

Suggested files:

- `manifest.json`: schema version, campaign/gate state, full production SHA/tree, source archive and binary/image digests, harness/observer/parser hashes, exact module artifacts, build commands and dependency/toolchain identity, effective config digests, environment fingerprint, workload seed/digest, run order and comparison roles.
- `protocol.json`, `workloads/`, `observer-dictionary.json`: phase durations, arrival schedules, payload bytes/hashes, backend program, polling rules, latency/allocation semantics, checkpoint policy, expected populations, predeclared tolerances and invalidation rules.
- `runs/<profile>/<scenario>/<revision>/<repeat>/run.json`: PID/process role, start/end timestamps, phase boundaries, offered/admitted/success/error totals, valid/inconclusive/failed state and reasons. JSON numbers have named units; unavailable values are null plus reason, not -1 masquerading as a measurement.
- Adjacent `requests.jsonl`, `executions.jsonl`, `populations.jsonl`, histogram files and `metrics.json`: identities, monotonic timings, status/resource classes, attempts, metric values with provenance and phase. Use compressed immutable files for volume; never drop slow/error samples.
- `checkpoints/`: heap/GC logs, histograms, dumps when needed, RSS/PSS/direct-buffer/thread/socket observations, retainer analysis and collection commands. Keep SDKs/backend/generator in separate process-role directories.
- `verification/`: exact commands, stdout/stderr, exit codes, XML/results, selected/skipped counts, profile mapping and R1–R8/later-risk evidence. `comparison.json` plus a human report contain per-run values, paired deltas, variability and acceptance decisions.
- `SHA256SUMS`: hashes and sizes of all payload files, with an external digest for the manifest or complete archive to avoid recursive self-hashing. Archive sources and binaries as well as Git references, so future dependency drift cannot erase reproducibility.

The parser must reject schema/config/workload mismatches, missing successful latency sample counts, absent repetitions and unaccounted admissions. Keep aborted runs and reruns with reasons. Freeze collection overhead and percentile conventions; any later harness change creates a new protocol version and requires remeasurement of B as well as C.
